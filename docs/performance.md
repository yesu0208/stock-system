## 시스템 구조와 측정 방법

주문은 세 단계를 거칩니다. 각 단계 사이는 Redis Streams로 연결되고, 서비스 간 이벤트는 Outbox 패턴으로 발행합니다.

1. **주문 접수 (stock)**: 주문 스트림을 소비해 저장 → 대기열 등록 → 응답 저장 → 발행.
2. **체결 (stock)**: 시세 틱이 들어오면 대기 중인 주문을 매칭하고, 대기열 순번을 방송.
3. **정산 (account)**: 체결 이벤트를 소비해 잔고와 보유 종목(user_stocks)을 반영.

각 컨슈머는 레코드별 PROCESSING/DONE 키로 중복 처리를 막습니다. stock 서버는 A/B 두 대가 종목을 나눠 맡습니다.

**측정 도구**

| 도구 | 용도 |
| --- | --- |
| Prometheus + Grafana | 단계별 타이머, 대기 시간, 처리량 대시보드 |
| k6 (ramping-arrival-rate) | 초당 20 → 50 → 100건 주문 부하 |
| 가짜 틱 생성기 (#178) | 장이 없어도 체결이 일어나도록 매도 체결 틱 주입 |
| EXPLAIN ANALYZE | 쿼리 실행 계획과 실제 시간 |

**측정 환경**: 로컬 PC (Ryzen 5 5625U, RAM 15GB) 위 WSL 2 (CPU 12, 메모리 7.4GB), docker-compose.loadtest.yml.

**측정 시 주의**: 15:40 MarketCloseJob(미체결 강제 취소)과 20:05 AfterMarketCloseJob 시간대를 피해야 합니다. 첫 기준선은 15:40과 겹쳐 1,428건이 취소돼 무효 처리하고 15:54에 다시 측정했습니다.

## 1부. 주문 접수 경로 (#169~#172)

네 번의 개선으로 주문 최대 대기는 686초에서 1.4초가 됐고, 처리량이 유입량을 따라가게 됐습니다.

| 단계 | 최대 대기 | 처리량 |
| --- | --- | --- |
| 기준선 | 686초 | 9 → 3건/초 (시간이 갈수록 하락) |
| #169 대기열 방송 축소 | 39.4초 | 24.4건/초 |
| #170 드레인 루프 | 18.4초 | 29.7건/초 |
| #172 종목별 병렬 처리 | 1.4초 | 유입량 그대로 추종 |

### #169 대기열 순번 방송을 바뀐 지점부터만

- **문제**: 처리량이 시간이 갈수록 떨어졌습니다 (9 → 3건/초).
- **원인**: 주문 한 건마다 대기열 전체의 순번을 다시 방송했습니다. 대기열이 길어질수록 비용이 O(N)으로 커졌습니다.
- **수정**: `QueuePositionBroadcastService.broadcastFrom` — 순번이 바뀐 지점부터만 방송.
- **결과**: 최대 대기 686초 → 39.4초.

### #170 배치가 가득 차면 쉬지 않고 바로 다음 배치

- **원인**: 컨슈머가 배치를 처리한 뒤 항상 스케줄 주기만큼 쉬었습니다. 쓰이는 메시지가 있어도 기다렸습니다.
- **수정**: `AbstractRedisStreamConsumer`에 드레인 루프 — `while (consumeBatch() == BATCH_SIZE) {}`.
- **결과**: 39.4초 → 18.4초, 24.4 → 29.7건/초.

### #171 원인 분석: 처리 시간의 70%는 DB 저장

- **한 일**: `OrderService`에 단계별 타이머 `order.register.step` (save / enqueue / response_save / publish)를 넣고 대시보드 패널을 추가했습니다.
- **발견**: 처리 30ms 중 save가 21ms (70%). HikariCP 커넥션 획득은 약 0ms — 풀 부족이 아니라 커밋 비용이었습니다.
- **확인 실험**: MySQL fsync를 끄자 save가 21ms → 4ms. 커밋마다의 디스크 동기화가 원인임을 확인했지만, 데이터 안전성 때문에 채택하지 않았습니다.
- **결론**: 한 건의 비용을 줄이기보다 동시에 여러 건을 처리하는 쪽으로 갔습니다 (#172).

### #172 종목별 병렬 처리

- **수정**: stock 컨슈머에 `partitionKey()` / `workerCount()` / `processInParallel` 추가. 주문은 stockCode로 파티션해 같은 종목의 순서는 지키고, 다른 종목은 동시에 처리합니다 (`redis.streams.order.workers: 4`).
- **결과**: 최대 대기 18.4초 → 1.4초. 처리량이 유입량을 그대로 따라갑니다.
- **한계**: 초당 250건을 넣어 보니 스트림 하나당 약 75건/초에서 멈춥니다. 배치 안의 가장 느린 파티션을 기다리는 배치 장벽 때문입니다 (10건 / (4 × 33ms)).

### 함께 한 정리: 장 마감 보호와 보안

- **#173 / #175**: 장 마감 후 들어온 주문은 MARKET_CLOSED 오류를 알립니다 (주문, 자동주문, 트레일링 스탑, OTOCO 컨슈머의 `publishError`). 취소 컨슈머는 MarketCloseCleanupService가 이미 강제 취소와 알림을 하므로 제외했습니다.
- **#174**: ALB 리스너 규칙 `block_actuator` (우선순위 5)로 `/actuator*` 외부 접근에 404를 반환합니다.

## 2부. DB 잠금과 인덱스 (#176, #177)

전체 행을 잠그던 조회를 한 행만 잠그도록 바꾸고, 자주 도는 조회 3개를 최대 약 870배 빠르게 했습니다.

### #176 한 사용자 계좌를 잠그면 모두가 멈춰던 문제

- **원인**: `user_accounts.username`에 인덱스가 없어 `SELECT … FOR UPDATE`가 테이블을 풀 스캔했고, InnoDB는 스캔한 **모든 행**에 잠금을 겁니다. 한 사용자의 정산이 다른 모든 사용자를 막았습니다.
- **수정**: account `V2__add_unique_username.sql` — `user_accounts(username)`, `user_stocks(username, stock_code)`에 UNIQUE. stock `V2__add_otoco_entry_order_index.sql`.

| 확인 항목 | 개선 전 | 개선 후 |
| --- | --- | --- |
| EXPLAIN (type / key / rows) | ALL / NULL / 7 | const / uk / 1 |
| 다른 사용자 계좌 잠금 시도 | 5초 대기 후 ERROR 1205 | 즉시 획득 |
| 같은 username 중복 삽입 | 허용됨 | 1062로 차단 |

### #177 자주 도는 조회에 인덱스

- **수정**: stock `V3__add_query_indexes.sql`, bff `V2__add_query_indexes.sql`.
- **측정**: 20만 행 데이터에서 EXPLAIN ANALYZE.

| 조회 | 개선 전 | 개선 후 | 배수 |
| --- | --- | --- | --- |
| Outbox (200ms마다 실행) | 201ms | 0.67ms | 약 300배 |
| 주문 내역 | 194ms | 0.22ms | 약 870배 |
| 미체결 주문 | 175ms | 29.6ms | 약 6배 |

**쓰기 비용은?** 인덱스는 쓰기를 느리게 할 수 있어 따로 확인했습니다. 부하 테스트의 save(약 24ms)와 handle(약 33ms)은 변화가 없었습니다. 비용이 드러난 것은 20만 행 대량 삽입뿐이었습니다 (5.56초 → 10.65초). 한 건 단위 쓰기에서는 fsync가 비용 대부분이라 인덱스 갱신이 드러나지 않습니다.

## 3부. 체결·정산 경로 (#178, #180, #181)

체결 뒤 방송 폭주를 없애자 병목이 정산으로 옮겨갔고, 정산까지 병렬화하자 k6 종료 28초 만에 모든 체결이 정산됐습니다.

| 지표 | #178 기준선 | #180 후 | #181 후 |
| --- | --- | --- | --- |
| k6 종료 후 잔여 체결 소진 | 6분 10초 | 0초 | 0초 |
| tradeMatching p95 | 8.52초 | 843ms | — |
| 대기열 방송 | 초당 약 2,900건, p95 433ms | 초당 352건, p95 85ms | — |

### #178 체결을 측정할 도구 만들기

- **문제**: 로컬에는 실제 시세가 없어 체결 경로를 측정할 수 없었습니다.
- **만든 것**: `FakeTickGenerator` (`loadtest.fake-tick.enabled`일 때만 동작). 브로커 원문 형식 `0|H0STCNT0|1|…`(47개 필드)으로 매도 체결 틱("5")을 `ExternalStockTickMessageDispatcher`에 넣습니다. 매도 체결이 들어와야 매수 주문이 체결되기 때문입니다.
- **설정**: 100ms 간격, 거래량 20, 가격 990~1000. stock A는 005930 / 000660 / 373220, B는 000810 / 032830 / 086790.
- **기준선에서 보인 것**: 호출 한 번에 최대 574건의 대기열 방송이 나갔고, 체결은 k6가 끝난 뒤에도 6분 10초 동안 밀렸습니다.

### #180 틱 하나당 방송 한 번

- **원인**: 주문 하나가 체결될 때마다 대기열 방송을 했습니다. 틱 하나에 여러 주문이 체결되면 방송도 그만큼 반복됐습니다.
- **수정**: `TradeMatchingService`의 매칭 메서드가 체결 여부(boolean)를 돌려주고, 틱마다 매수/매도 별로 `broadcastQueuePosition`을 한 번만 호출합니다. 체결 로직은 그대로이고 대기열 정보 방송 횟수만 바뀝니다.
- **결과**: 잔여 체결 0초, tradeMatching p95 8.52초 → 843ms. 체결이 빨라지자 정산이 따라오지 못해 최대 대기가 214.6초로 늘었습니다. 병목이 다음 단계로 옮겨간 것입니다.

### #181 정산도 사용자별 병렬 처리

- **수정**: account 컨슈머에 드레인 루프와 파티션 처리를 적용했습니다. `RedisTradeExecutedEventConsumer.partitionKey`는 payload의 `username`을 쓰므로 같은 사용자의 정산 순서는 지켜집니다 (`redis.streams.trade-executed.workers: 4`). `processRecord`에는 `acquired && !done` 가드를 두었습니다.
- **결과**: 정산 최대 대기 214.6초 → 0.79초, 처리량 80건/초.
- **정합성**: 체결 8,299건 = trades = 정산 반영 = user_stocks 합계. DLQ 0, 오류 0.

## 측정 중 발견한 버그: 주문 5건 유실 (#179)

부하 테스트 결과를 대조하다 주문 5건이 사라진 것을 발견했고, 수정 후 유실은 0건이 됐습니다.

- **원인**: Redis Streams 레코드 ID는 스트림마다 따로 매겨집니다. A/B 서버의 스트림에서 같은 ID가 나오면, 중복 방지 키가 겹쳐 두 번째 주문을 "이미 처리함"으로 보고 건너뛰었습니다.
- **수정**: 처리/재시도 키에 스트림 키를 포함 — `processed:{ns}:{streamKey}:{id}`.
- **교훈**: 처리량만 보지 않고 건수를 끝까지 맞춰 본 덕분에 찾은 버그입니다. 이후 모든 측정은 주문 수 = 체결 = 정산 = 보유 합계를 확인합니다.
